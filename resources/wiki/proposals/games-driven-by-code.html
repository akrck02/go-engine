9. 3D games driven by code

Status: done, pending the author’s review · Author’s approval: proposal ☑ (2026-10-21, “Okay”) plan ☑ (2026-10-21, “Si”)

Why

The engine serves games whose scenes are arranged in the editor: models from .glb files, cameras placed by hand, keys for input. An online 3D game made mostly in code needs more.

  • Its vehicles are built from designs at run time.
  • They move every frame.
  • Its effects glow or fade.
  • Its camera chases the player.
  • On the 3DS it uses the slider’s depth, both screens, and every control the console has.
  • On the desktop it captures the mouse.
  • It ships for Windows and macOS.

Without these, such a game has to skip the engine and draw with Go Renderer on its own. One game is waiting on them now; every 3D game in code will want them.

Out of scope

  • Networking itself: the game brings its own (Go for 3DS has TCP and TLS).
  • Sound in the engine: the game uses Go Sound directly. R10 only keeps the loop fair to it.
  • Editing meshes from code in the editor: they exist only while the game plays.
  • Signing and notarising macOS programs, and Windows installers.
  • A text field of the engine’s own: a game shows go-ui’s over the 3D window (R4’s layer, for go-ui).

Design

What is there already

Go UI’s window on the 3DS already draws the top screen in stereo with the slider (R6), paints the scene’s own drawing (World.Overlay.Drawing) in each eye (R4 on the 3DS), and yields each frame (runtime.Gosched, R10). Go Renderer’s nodes have Moving (R2), and its materials are lit, unlit, translucent and double-sided (most of R3). The engine only has to reach them.

In the engine

  • Meshes from code (R1, R2): Node.SetMesh(*scene.Mesh) replaces the node’s geometry, and Node.SetMoving(bool) sets Go Renderer’s flag on it, kept when a scene is copied for playing. Games use Go Renderer’s scene.Mesh and scene.Material as they are: a type of the engine’s own would only copy them.
  • Camera (R5): scenefile.Camera gains near and far (metres; 0 keeps today’s 0.05 and 2000), shown in the inspector. Node.Camera() and Node.SetCamera() let code change them.
  • Over the 3D (R4): engine.SetOverlay(func(list *draw2d.List, width, height float32)) draws each frame over a 3D scene. It goes to Go UI’s new SceneView.Drawing, which Go UI paints over the scene and under the interface on the desktop and phones (its window used to overwrite World.Overlay.Drawing with the interface), and on the 3DS’s top screen in each eye. SetBottomScreen becomes SetInterface: the bottom screen on the 3DS, over the window elsewhere (login fields).
  • Below, in 3D (R7): engine.SetSecondScreen(scene) gives the 3DS’s bottom screen a scene of its own, with the interface over it.
  • Input (R8): engine.Input gains Stick(), CStick(), Gyroscope(), Touches() and MouseMovement(); L, R, ZL, ZR and START become keys with Down and Pressed. SetPointerCaptured(bool) hides and holds the desktop’s pointer.
  • Hooks (R9): engine.BeforeBehaviours(func(context *Context)) runs first in each step, with the frame’s context (its Node nil), in the game and in the editor’s Play. engine.BetweenFrames(func()) runs once at the start of the next step. On the 3DS that is outside the frame being drawn, where the system keyboard can take both screens.
  • Releases (R11): Build gains “Release workflow”. It writes .github/workflows/release.yml into the game: Go builds the game on GitHub’s Windows, macOS and Linux machines and attaches each program to a release. Building for another system from Linux is not taken: GLFW needs cgo, and so a C compiler and the system’s own libraries for each target.

In the author’s libraries (each on a feature/ branch, with the author’s permission)

  • Go Renderer: Material.Additive (light adds to what is behind: beams, sparks) in OpenGL, Metal and ctr. The C-stick and the gyroscope in ctr.Reading, as Go for 3DS reads them.
  • Go UI: SceneView.Below (a scene and camera for the bottom screen, the interface painted over it), Options.KeepStart (START reaches the game instead of quitting), and a scene’s LockCursor passed on to the window (Go Renderer’s window loop applies it).

Result

After the build, at the author’s word (“the 3DS’s things should be generic”), the engine’s names say what a control or a screen is on any device, not on the 3DS: SetSecondScreen, RightStick, SecondScreenTouch, engine.Turn, ButtonLeftShoulder and the rest. The editor’s Play also shows a 3D game at its screen’s shape, with the second screen under the 3DS’s hinge (Go Renderer feature/scene-area: DrawIn; Go UI feature/scene-area: scene areas).

Built, on feature/ branches until the author merges and releases them:

  • go-engine feature/engine: R1–R5 and R7–R9 in the engine, R11’s workflow, and examples/lighthouse. Seen working in the editor’s Play and in Azahar at 60 frames a second.
  • Go UI feature/scene-drawing: SceneView.Drawing, SceneView.Below, Options.KeepStart, and a scene’s captured pointer reaching the window.
  • Go Renderer feature/motion-controls (with feature/additive in it): Material.Additive and the C-stick and gyroscope.

The review found 14 things: all fixed, among them the stick’s sign (Input.Move read the stick’s forward the wrong way before this change too), the frame hook running again for the bottom screen’s scene (hooks now run in Scene.PlayFrame, the main scene’s frame), and the gyroscope left on when its coefficient could not be read.
