10. Names for any device

Status: done, pending the author’s review · Author’s approval: proposal ☑ (2026-10-21, “Si”) plan ☑ (2026-10-21, “Si”)

Why

The guidelines now ask for generic functions: named, and shaped, for what they do on any device, not for the first one that needed them, as nobody knows how they will be used later. An audit of the author’s Go libraries found nine places that break it. Most of them are in go-engine’s building and running for each target, and in the word “console” standing for the 3DS. A second console, or a game pad’s right stick, would already have nowhere to go.

Nothing of go-engine’s is used by others yet beyond its own sample and one game in development, so this is the cheapest moment to rename.

What

R3 A game has one application id (applicationId in engine.json), which each target turns into what it needs; androidId is still read, so older projects keep working test an old androidId is read as the application id
R4 Accepting a tool’s licence is one set of functions that take the tool (ReadLicence, Licence, AcceptLicence, DeclineLicence), not Android’s own test of the licence flow through the generic functions
R5 “Console” no longer stands for the 3DS: names that mean the 3DS say so (Nintendo3DSTarget, the 3DS’s emulator), and names that are general become general (DeviceAddress, SendToDevice); engine.json’s consoleAddress is still read tests of the renamed settings; an old engine.json still opens

Out of scope

  • Packages that exist for one platform only (Go Renderer’s ctr, Go for 3DS’s own) keep their platform’s names inside.
  • New targets: this only makes room for them.
  • Error codes across Go Sound: it uses plain sentinel errors throughout, which is its own change.
  • Keeping the old names as aliases. Nothing is released with them except go-engine v0.0.x, which is still experimental. The two settings in engine.json are read under both names, because they live in people’s files.

Design

Go Renderer: a game pad on a computer (R1)

input.State gains RightStickX and RightStickY, as StickX and StickY are for the main stick. The desktop’s window loop reads the first game pad GLFW knows (GetGamepadState, which maps every pad to one layout) into both sticks, each with a dead zone. The 3DS’s ctr.Controls puts the C-stick into the right stick once the motion controls are on. Go Renderer’s feature/ branch, as before.

go-engine

  • Sticks (R1): Input.RightStick reads RightStickX and RightStickY, whatever filled them; the engine’s own reading of the C-stick goes.
  • Targets (R2, R5): the project package gets a Target type (Desktop, Nintendo3DS, Android) with Build, PlayOn, PlayInEmulator and StopOn, each choosing the target’s way inside: today’s Build3DS, SendTo3DS, BuildAndroid, PlayOnAndroid, StopOnAndroid, EmulatorCommand and PlayCommand become their private parts. Sending to the 3DS is playing there, as its Homebrew Launcher starts what it is sent (built: the plan’s separate SendTo was one verb too many). A target without something (an emulator of its own) is refused with a code. The editor’s BuildTarget becomes project.Target, and ConsoleTarget becomes Nintendo3DS; the editor’s PlayOn(target) and PlayInEmulator(target) replace PlayInWindow, PlayOnDevice, SendToConsole and the old PlayInEmulator.
  • Settings (R3, R5): Settings.ApplicationID (applicationId) and Settings.DeviceAddress (deviceAddress). Reading engine.json takes androidId and consoleAddress when the new names are missing, and saving writes only the new ones.
  • Tools (R5): build.Tools.ConsoleEmulator becomes Nintendo3DSEmulator (nintendo3dsEmulator in tools.json, the old name still read); and the Play workspace’s ConsoleScreen shape becomes Nintendo3DSScreens.
  • Licences (R4): the editor’s licence sheet takes a tool’s name; Android’s SDK is today’s only tool with one.
  • Leftovers (R6): SetBottomScreen goes; SceneMenu’s comment is made general.

Go for 3DS and Go Sound (R7, R8)

Each on a feature/ branch: Go for 3DS’s bottom package is renamed secondscreen, its sample with it; Go Sound defines ErrOutputUnavailable in sound.go, and the 3DS’s output returns it.

Alternatives not taken

  • Aliases for the old function names: they would keep the old names alive in new code.
  • One Do(target, action): four verbs read better, and each has its own errors.

Result

Built, on feature/ branches until the author merges them:

  • go-engine feature/engine: R1–R6 and R9. The second screen’s guide is now docs/5-guides/8-the-second-screen.md.
  • Go Renderer feature/game-pad (on feature/scene-area): a computer’s game pad into both sticks, and the 3DS’s C-stick into the right one (R1).
  • Go Sound feature/output-unavailable: ErrOutputUnavailable (R7).
  • Go for 3DS feature/second-screen: the secondscreen package (R8).

The review found 14 things, all fixed or answered here:

  • the guide and test names that still said “bottom screen” or “console”;
  • a stale comment;
  • a test for a game sent with nothing to watch;
  • the game pad made private, and letting its sticks go only when it is unplugged;
  • targets outside the list given a name instead of a panic;
  • Go Sound’s failure made through one tested function.

Two things stay as they are, for a person to judge:

  • GLFW’s game pad reading allocates while a pad is plugged in, because its Go binding returns a new state each time; avoiding it would need cgo of the engine’s own.
  • go-engine pins Go Renderer’s unmerged feature/game-pad by pseudo-version: merge Go Renderer, Go UI, Go Sound and Go for 3DS first, then pin go-engine to their versions before it is released.
