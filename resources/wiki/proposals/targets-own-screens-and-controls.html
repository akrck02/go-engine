11. Each target’s own screens and controls

Status: building · Author’s approval: proposal ☑ (2026-10-21, “dale”) plan ☑ (2026-10-21, “si”) · Controls redesign and R8 ☑ (2026-10-21, “implementalo”, “si añade trazos”)

Why

A game made for several devices lays out its interface and reads its controls differently on each, and today it has to do that by hand:

  • pairs of files split by build tags (controls.go and controls_nintendo3ds.go);
  • constants such as “has a touch screen”;
  • on the desktop, a picture of the 3DS’s touch screen pasted into the middle of the window, with mouse clicks turned into touches.

That is one device’s layout imposed on another. A game should say what it shows and what the player does, and each target should say where and with which buttons.

Out of scope

  • Touch gestures beyond the pointer (swipes, pinches) as actions.
  • A full settings menu for players; the engine gives what one needs (R3), not the menu.
  • Consoles other than the 3DS: the design makes room for them.

Design

Targets at run time

The engine knows which target it runs on (a constant per build: desktop, nintendo3ds, android, web), named as engine.json names them. project.Target gains Web’s name for the settings, though building for the web stays out of this change.

Actions (R1–R3)

engine.json gains actions. Each action lists, per target, the inputs that press it, as words a person can read and type:

"actions": {
  "menu": {"desktop": ["Tab", "P", "Pad Start"], "nintendo3ds": ["Start"], "android": ["Back"]},
  "fire": {"desktop": ["Space", "Mouse Left", "Pad A"], "nintendo3ds": ["R", "A"]},
  "turn": {"desktop": ["A-", "D+", "Left-", "Right+", "Stick X"], "nintendo3ds": ["Circle X", "Left-", "Right+"]}
}
  • A button input presses the action: a key, a mouse button, a pad’s button, a 3DS’s button, Android’s back.
  • An axis input moves it from -1 to 1: a stick’s axis, or a button with - or + after it.
  • Input.Action(name) gives the action’s state this frame: Down, Pressed, Released and its Value (-1 to 1; 1 while a button holds it). One call, one value returned: Go has no overloading, so Input.Down keeps taking keys, which games read today (R7).
  • The bindings are read once into a table of the engine (engine/actions.go), so reading an action each frame is a map lookup and some booleans, with nothing allocated.
  • Rebinding (R3): Input.Rebind(action, inputs) changes the current target’s inputs, and engine.SaveBindings keeps them in the user’s configuration folder (on a 3DS, on the SD card). The game’s own engine.json stays as its author wrote it.
  • The editor (R2): a workspace of its own, Controls, designed with the author in a canvas before it was built. The actions are cards on the left, each in a soft colour of its own, with buttons to rename it, switch its kind and remove it, and chips for the controls that do it. The device is drawn in the middle in thin grey lines, as Lucide draws icons, at its real proportions, in tabs: Gamepad, Keyboard and mouse (both kept for desktop and web), Nintendo 3DS and Mobile (android). A control that does an action takes its colour and names it at the drawing’s edge with a dotted line. Clicking one opens a panel beside it: a field to find or create an action, and the actions it can do, one chosen (a button presses; a stick’s two axes each move one). Every change is saved in engine.json at once, and Ctrl+Z undoes it in this workspace.
  • Strokes (Go Renderer): the drawings’ curves need lines, which draw2d did not have. draw2d.Path and List.Stroke draw a path into a smoothed mask kept in the path, shown as a tinted picture, so every backend that draws pictures draws strokes.
  • Touch controls (R8): engine.json’s touchControls lists sticks and buttons, each placed and sized as shares of the screen. On Android the game draws them over its view and reads the fingers on them; actions bind them as Touch <name>, and a stick as Touch <name> X and Y. The Mobile tab’s Layout designs them: add, drag, resize, rename, remove.

Surfaces (R4, R5)

engine.SetSurface(name, paint func(context *ui.Context)) names what the game shows. engine.json’s surfaces says, per target, where each goes:

Place What it is
over over the game’s view, aligned to an edge or a corner, with a size
window a floating window over the view, opened and closed by an action
second-screen the second screen (a 3DS’s), touchable; several share it in a column
sheet a sheet from the bottom (Android), opened and closed by an action
none not shown on that target

The engine lays each surface out with what Go UI has (Within, Overlay, PanelWith, Sheet). SetInterface becomes the surface interface, placed on the second screen on the 3DS and over the view elsewhere, as today (R7). SetSecondScreen’s 3D scene stays as it is. The editor’s Play gains a target to preview beside the shapes it has (R5): each target’s places for its surfaces.

Fullscreen (R6)

  • Go Renderer: input.State.SetFullscreen and Fullscreen, requested like the captured pointer and applied by the window loop with GLFW (SetMonitor, back to the window’s last place and size). The browser loop calls the Fullscreen API on the next key or click. The function keys F1 to F12, and a game pad’s buttons, join input.Key and the state.
  • Go UI: a scene’s request reaches the window, as its captured pointer does.
  • go-engine: engine.SetFullscreen(bool) and engine.Fullscreen(); engine.json’s window (windowed or fullscreen) per target; an action fullscreen, bound to F11 and Alt+Enter on the desktop unless the game binds it otherwise.

Alternatives not taken

  • Bindings in code: engine.json lets the editor show them and a player change them without a build.
  • One layout file per target: a table per surface keeps a surface’s places side by side.
